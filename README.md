# Moai Idle Game (모아이 키우기)
기존 팀 프로젝트로 개발했던 Merge 기반 방치형 게임을 개인 프로젝트로 리빌딩한 프로젝트입니다.  
플레이 루프와 시스템 구조를 재구성하고, 콘텐츠 확장과 모바일 최적화를 중심으로 개선했습니다.

## 프로젝트 개요
- 개발 환경 : Unity 2D
- 사용 언어 : C#
- 개발 기간 : 2025년 06월 ~ 2025년 11월
- 개발 인원 : 1인 (개인 프로젝트)
- 플랫폼 : Android (Mobile)

## 전작 대비 개선 및 차별점
- 캐릭터 수 확장 → 수집 요소 강화
- 미니게임 비중 축소 → 성장 / 수집 루프에 집중
- 보스 스테이지 제거 → 전투 부담 완화
- 일일 보상, 업적, 오프라인 보상 추가 → 재접속 동기 부여
- 자동 소환 / 자동 합치기 기능 추가 → 반복 조작 피로도 감소

## 기술적 고민
### 1. 반복 생성 오브젝트 최적화
- 캐릭터, 골드 텍스트, 보상 이펙트처럼 반복 생성되는 오브젝트가 많아지면서 성능 저하가 발생할 수 있었습니다.
- Object Pooling을 적용하여 오브젝트를 미리 생성하고 재사용하는 구조로 변경했습니다.
- 이를 통해 불필요한 Instantiate / Destroy 호출을 줄이고, 모바일 환경에서 보다 안정적인 플레이가 가능하도록 개선했습니다.
### 2. PlayerPrefs 저장 방식의 한계 개선
- PlayerPrefs는 간단한 값 저장에는 적합했지만, 캐릭터 상태, 재화, 업적처럼 구조화된 데이터를 관리하기에는 한계가 있었습니다.
- 저장 방식을 JSON 기반 구조로 변경하고, SaveData 형태로 데이터를 묶어 저장 / 로드하도록 구성했습니다.
- 이를 통해 저장 데이터 관리가 쉬워졌고, 기능 추가 시 데이터 확장이 수월해졌습니다.

## 회고
### 주요 어려움
 - 팀 프로젝트에서 구현했던 구조를 개인 프로젝트로 다시 만들면서, 단순히 기능을 추가하는 것보다 기존 구조를 개선하는 과정이 더 중요했습니다.
 - 콘텐츠가 늘어나면서 저장 데이터, UI 갱신, 오브젝트 생성 흐름을 일관되게 관리하는 부분이 어려웠습니다.
 - 특히 반복 생성 오브젝트와 대량 저장 데이터를 관리하면서, 초기에 구조를 잘 잡는 것이 중요하다는 점을 느꼈습니다.
### 배운 점
- 반복 생성되는 오브젝트는 초기 단계부터 Object Pooling 구조를 고려해야 성능 관리가 수월하다는 점을 배웠습니다.
- PlayerPrefs처럼 간단한 저장 방식은 데이터가 많아질수록 관리가 어려워지기 때문에,  
  JSON 기반 구조로 데이터를 묶어 관리하는 방식의 필요성을 경험했습니다.
- 기능을 확장하기 전에 데이터 구조와 시스템 책임을 먼저 분리해야 유지보수와 기능 추가가 쉬워진다는 점을 배웠습니다.
