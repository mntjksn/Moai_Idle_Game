# Moai Idle Game (모아이 키우기)
기존 팀 프로젝트로 개발했던 Merge 기반 방치형 게임을 개인 프로젝트로 리빌딩한 프로젝트입니다.  
플레이 루프와 시스템 구조를 재구성하고, 콘텐츠 확장과 모바일 최적화를 중심으로 개선했습니다.

## 프로젝트 개요
- 개발 환경 : Unity 2D
- 사용 언어 : C#
- 개발 기간 : 2025.06 ~ 2025.11
- 개발 인원 : 1인 (개인 프로젝트)
- 플랫폼 : Android (Mobile)

## 전작 대비 개선 및 차별점
- 캐릭터 수 확장 → 수집 요소 강화
- 미니게임 비중 축소 → 성장 / 수집 루프에 집중
- 보스 스테이지 제거 → 전투 부담 완화
- 일일 보상, 업적, 오프라인 보상 추가 → 재접속 동기 부여
- 자동 소환 / 자동 합치기 기능 추가 → 반복 조작 피로도 감소

## 기술적 고민
### 1. 반복 생성 오브젝트 최적화
- 캐릭터, 골드 텍스트, 보상 이펙트처럼 반복 생성되는 오브젝트가 많아지면서 성능 저하가 발생할 수 있었습니다.
- Object Pooling을 적용해 오브젝트를 미리 생성하고 재사용하는 구조로 변경했습니다.
- 불필요한 Instantiate / Destroy 호출을 줄여 모바일 환경에서 더 안정적인 플레이가 가능하도록 개선했습니다.
### 2. PlayerPrefs 저장 방식의 한계 개선
- PlayerPrefs는 간단한 값 저장에는 적합했지만, 캐릭터 상태, 재화, 업적처럼 구조화된 데이터를 관리하기에는 한계가 있었습니다.
- 저장 방식을 JSON 기반 구조로 변경하고, SaveData 형태로 데이터를 묶어 저장 / 로드하도록 구성했습니다.
- 저장 데이터 관리가 쉬워졌고, 기능 추가 시 데이터 확장이 수월한 구조로 개선됐습니다.

## 회고
### 주요 어려움
  #### 1. 기존 구조의 한계 파악
  - 팀 프로젝트 코드를 리빌딩하면서 단순히 기능을 추가하는 것보다 기존 구조의 문제를 먼저 파악하고 개선하는 과정이 더 어려웠습니다.
  - 특히 PlayerPrefs 기반 저장 구조는 데이터가 늘어날수록 관리가 어려워져 초반에 구조를 전면 변경하는 결정을 내려야 했습니다.
  #### 2. 모바일 성능 관리
  - 오브젝트가 늘어날수록 간헐적으로 프레임이 떨어지는 문제가 발생했고, Object Pooling 적용 범위를 점진적으로 넓혀가며 해결했습니다.
### 배운 점
- 기능 구현 전에 데이터 구조와 시스템 책임을 먼저 분리하는 것이 유지보수와 기능 확장에 중요하다는 것을 배웠습니다.
- 리빌딩 과정에서 전작의 구조적 문제를 직접 경험하면서, 설계 단계의 결정이 이후 개발 전체에 영향을 준다는 점을 느꼈습니다.
- Object Pooling과 JSON 기반 저장 구조를 직접 적용하면서 성능과 확장성을 함께 고려하는 습관을 기를 수 있었습니다.
